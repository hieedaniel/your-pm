# 知识库生成说明（docs-kaiyi）

知识源：`【海康智慧园区解决方案】凯翼汽车智慧园区解决方案-20220826.pptx`（41 页）。
暂时不接 MCP 时，实时链路的检索就查这里。

## 三个脚本，按顺序跑

```bash
# 1) 从 PPT 抽全文（slidep 是 PPT skill 提供的命令）
OUT="$(mktemp -d /tmp/slidep.XXXXXX)"
slidep inspect "<pptx 路径>" --out "$OUT"
cp "$OUT/slides.md" _kb/kaiyi.md

# 2) 解析成「页 → 文本」
python _kb/parse.py _kb/kaiyi.md

# 3) 按主题重组成知识库文档（会整体重建 docs-kaiyi/）
python _kb/build_docs.py
```

## 为什么是「重组」而不是「一页一篇」

41 页里 4 页是目录、1 页封面、1 页法律声明，一页一篇会灌进大量空壳，
BM25 的 df 统计被稀释，检索质量反而下降。同一主题分散在多页（安消在 19/20/21），
合并后一张卡能给出完整依据，而不是碎片。

最终 19 篇，页码对应关系写在每篇的 `source:` 字段里，卡片上直接显示「P15、P16」。

## 清洗规则（都在 build_docs.py 里）

| 噪音 | 处理 |
|---|---|
| 每页左侧导航「数据运营中心/生产制造管理/…」 | 按行过滤。导出结果是**一行一个**，不是一行 |
| `- •`、`- n`、`- l`、`- Ø` 导出残留 | 去前缀 |
| `8\~12%`、`\&` 这类 Markdown 转义 | 反转义 |
| 架构图上竖排的短标签 | 串成一行「图示要素：A、B、C」，可读性比竖排好 |
| 截图里的示意标注（`车牌：浙AXXXXX`） | 丢弃，那是配图元素不是方案内容 |

## front-matter 字段

| 字段 | 作用 |
|---|---|
| `title` / `visibility` / `as_of` / `tags` | DocStore 读取，`tags` 同时用于 ASR 热词 |
| `source` | 卡片上的出处，含 PPT 页码 |
| `say` | **客户实际会怎么说**。只参与检索加权，不进热词（「订了不用」当热词是噪音） |
| `use_when` | 这条知识什么时候该用。**必须放 front-matter**，写进正文会让演示问句命中自己那段话，卡片永久 1.00 分且全是元信息 |

## 已知边界

- 方案是 **2022-08-26** 的版本，卡片上会如实显示 `as_of 2022-08-26`。客户问「现在支持吗」时，
  这张卡只能证明「当年方案里有」，不能证明「现在还能交付」。
- 检索是关键词 BM25，不是语义检索。客户换一种说法就命中不到 —— 靠 `say` 词表补救，
  补不到的地方系统会沉默（不推卡），不会推一张错的。
- 视觉信息未入库：架构图的连线、方向、配色都没进文本，只能靠「图示要素」列表间接体现。
